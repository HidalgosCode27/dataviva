From the Field to the Database: Two Data Pipelines for Assistance Programs

Assistance data collected on phones has to end up somewhere permanent, clean and queryable, and the households that need help first have to be identifiable fast. Two scripts I wrote for that: a Kobo-to-PostgreSQL synchronization with its rollout plan, and a household prioritization model built for a natural-disaster emergency.

About this page. Both pieces are SQL and Python I wrote for assistance programs. Everything shown here is documentation: the household table and the sample run are synthetic, no credentials appear (the script reads them from environment variables) and no data about people in need is included. Names, identifiers and locations have been generalized.

01 — SynchronizationKobo to PostgreSQL: making field data permanent

Assistance deliveries are recorded in a KoboToolbox form, signature included. But Kobo is a collection tool, not a system of record: the data has to land in the central PostgreSQL database, without duplicates, without losing anything that doesn't match, and without depending on whoever built the form. The script is designed to run on a daily schedule and to be safe to run twice.

Synchronization flow

One daily run, from form to database

Design decisions

  • Idempotent by design.Each Kobo submission has a unique _id stored as kobo_id with a UNIQUE constraint, and inserts use ON CONFLICT DO NOTHING. Running the script twice never creates duplicates, and the next run starts from the highest ID already loaded.
  • Nothing is discarded.If a submission's person ID is not in the master table, it goes to pending_records with the complete JSON and a resolved flag for manual review, instead of being rejected.
  • Every run leaves a trace.A sync_log row records new records, pending records and any error, written even when the run fails.
  • Signatures handled with a safety rule.Until institutional storage exists, only the Kobo attachment link is stored, and the script's header warns never to delete submissions from Kobo while that setting is on, because the signatures only exist there.
  • No secrets in code.URL, token, form UID and database connection come from environment variables.

The core of the script

02 — RolloutFrom script to operation: the implementation plan

A script that works on a laptop is not a pipeline. The second document I wrote for this project is the rollout plan: six steps from an empty database to a pipeline someone else can maintain. Most of the risk is not in the Python. It is in the ID format, the schedule and the handover.

  1. 1
    Create the tables

    Run the schema to create the master table of people in need, the records table, the pending table and the run log. Then load the master table and check that every ID has exactly the format the form produces: case, leading zeros, hyphens. One character of difference breaks the match.

  2. 2
    Collect the connection details

    Four things from the institutional Kobo account: the form UID (visible in the form URL), an API token, the instance URL and the internal question names (the "name" column, not the visible label) for ID, assistance type, date, signature and remarks.

  3. 3
    Configure the script on the server

    Copy the script, install the two dependencies, map the internal field names and set the environment variables. Signatures stay as links while no institutional storage exists, which means nothing can be deleted from Kobo. The first run starts from zero and brings in every existing record: run it by hand and check that the count matches Kobo.

  4. 4
    Schedule it

    A scheduled task on the server itself, once a day in the early morning, so no personal computer has to be on and nobody has to be connected. It needs someone with administrative access, once. And it needs a failure alert by email: a pipeline that fails silently is worse than none, so the signal is that the run log stops receiving rows.

  5. 5
    Pilot for one to two weeks

    Ideally on a copy of the database, otherwise with daily monitoring of the run log. Simulate the edge cases below and compare Kobo and SQL totals every day. If the pending table fills up, the problem is how the master table was loaded.

  6. 6
    Institutional safeguarding

    Document where the script lives, where the variables are, how the form's preload list is regenerated, what to do if it fails and who maintains it. Review the pending table weekly. When a new list arrives, load the database first and regenerate the form's list from it: the database always leads, never the other way around. Leave the signature-storage decision explicitly open.

03 — PrioritizationAfter a natural disaster: who gets help first

After a natural disaster, assistance had to be planned household by household, and the households with the most vulnerable members were not always the ones with the most visible damage. The model turns two inputs into a single ranked list: how badly the home was damaged, and which vulnerabilities live inside it.

Eight vulnerability tiers

  • 1Disability + older adult + child
  • 2Disability + older adult
  • 3Disability + child
  • 4Disability only
  • 5Older adult + child
  • 6Older adult only
  • 7Children only
  • 8Adults only, no vulnerable member

One score, damage first

Each household gets a tier from 1 to 8 based on whether it includes a person with a disability, an older adult or children. That tier is then combined with the damage level, where 1 is the most severe:

priority = tier + 10 × (damage_level − 1)
list sorted ascending: lowest score is served first

Because the tier never exceeds 8 and the damage step is 10, damage level decides the band and vulnerability decides the order inside it. Every score maps back to exactly one pair of damage level and tier, so the ranking is fully explainable to a field team.

A design choice worth stating. Putting damage ahead of vulnerability is a policy decision, not a technical one. It suits a response where shelter safety is the first filter. A program that prioritizes protection needs would flip the weights, and because the logic is a single formula, changing it is a one-line edit.

04 — Next iterationWhat I would improve

  • Isolate bad rows in the sync.One submission with a missing required field currently rolls back the whole batch and blocks every later run. Handling each record in its own savepoint would send only the bad one to pending_records.
  • Make the log tell the truth after a failure.The run counters are incremented before a possible rollback, so a failed run can log inserts that never committed. Resetting them on error fixes it.
  • Make the scoring re-runnable.The damage step adds to the tier already stored, so running it twice compounds the score. Computing tier and damage in a single expression, or in a view, removes that risk, and a final tiebreak (household size or collection date) would make the order deterministic.
