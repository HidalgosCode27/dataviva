From a Shared Spreadsheet to a Shift Reporting Database

Every shift, team leaders filled in a workbook by hand: who turned up, what moved, which machines were down. The data existed, but it was unusable — one file per site, formulas that broke, no history. Replacing the workbook with a validated form writing to a database changed what the data could be asked to do.

About this page. Built as part of a logistics process-improvement project in a distribution warehouse. The company, the sites and the operational constants are deliberately not named, and every figure shown is synthetic. Credit where it is due: the Excel logic this form replicates was built by Kristofer Salcedo. The form itself — the interface, the validation layer, the data model and the code — is mine.

01 — The problemA spreadsheet doing a job it was never built for

The shift report was a workbook with a sheet per site and a database sheet behind it. A team leader finishing a shift opened it, typed the names of the operators on shift, marked attendance and role for each one, logged incidents, ticked off the machinery, and let a column of lookups and COUNTIF formulas produce the shift's totals.

It worked, in the sense that a number came out at the end. But as a data-capture tool it had four problems that no amount of tidying fixes. Names were typed, so the same operator existed in three spellings. Nothing was validated, so a shift could be saved with an operator marked present and no role assigned, and the totals would still compute. Each save overwrote the file, so there was no history to compare one month against another. And because every leader worked on the same file, two people reporting at the same time meant one of them lost their work.

The requirement I set before writing anything: a leader should be able to file a shift report in the same few minutes it took them in the workbook, and the result should land in a database that can be queried.

02 — What I builtA form at the point of capture, a database behind it

Shift reporting flow

Dashed boxes are configured but not the default deployment

The form is a Python application the leaders open from a shortcut — no terminal, no install steps for them. The roster and equipment list load from reference files, so the leader picks a name from a list instead of typing it, and picking their own name filters the list down to the operators in their own group: the same logic the workbook did with a nested lookup, but done once, in one place.

The report itself keeps the structure the leaders already knew, because the aim was not to retrain them: shift header, their own team, support operators lent from other groups, incidents, and an equipment checklist in two categories where each machine is marked operational, awaiting maintenance or stopped.

03 — The data modelFour tables instead of one sheet

The workbook flattened everything onto one row per shift, which is why nothing could be asked of it afterwards. The database splits the report into the things that actually vary in number: a shift has one header, many operators, many incidents and many machines.

Two design choices here matter more than the column lists. A shift is identified by date, site, leader and shift, and filing the same one twice replaces the earlier version instead of adding a second copy — the duplicate-report problem solved at the point where it was created rather than cleaned up downstream. And the whole report is written in a single transaction: a report either lands complete, with its operators, incidents and machines, or it does not land at all.

04 — ValidationThe rules that run before anything is saved

This is the part that changed the data quality, and it is the part a spreadsheet could never have. The form separates what it refuses from what it only flags — a hard stop on a genuine contradiction, a warning where the leader may well be right and just needs to see it.

  • refusesAn operator marked present with no role assigned, or a role filled in with no name against it
  • refusesThe same person appearing twice in one report, including the leader appearing among their own operators
  • refusesA report with no operators at all
  • refusesAn incident missing its document reference, task or type
  • refusesA time for the next inbound order with no date to go with it
  • flagsA role assigned to someone recorded as absent, on leave or signed off — it still counts, but the leader is told it will
  • flagsA machine marked not operational with no observation explaining why
  • flagsAn attendance count that does not reconcile against the sum of assigned roles

That last one is the workbook's own cross-check, kept deliberately. It is a crude test — available operators should equal the roles handed out — and it catches most of what a tired leader at the end of a shift gets wrong.

05 — What the form calculatesDerived once, stored, not recomputed in every report

The totals the workbook produced with formulas are computed in the application and stored on the report. The point is that the arithmetic lives in one place and the stored history does not shift when someone edits a formula.

available = team − on leave − signed off − absent + support
tasks = unloads + loads + orders + bays located
pallets = tasks × agreed pallets-per-task factor
productivity = tasks ÷ (available − reconditioning)
equipment availability = operational ÷ total checked

The denominator in the productivity line is the one worth defending. Operators assigned to reconditioning are present and available, but they are not doing the movements the numerator counts, so leaving them in the denominator would penalise a shift for how its people were allocated rather than how much it moved. Equipment availability is reported per category rather than as one blended figure, because the two categories fail in different ways and at different costs.

06 — Decisions that matteredChoices I would defend in a review

  • One codebase, two databases.The application talks to its database through a single abstraction layer. With nothing configured it writes to a local file, so it runs on a laptop with no setup and no account. Given a connection string it writes to hosted PostgreSQL instead, with no change to the code. That meant the form could be tested and used before anyone had to approve infrastructure — and the migration path was already there.
  • No personal data in the repository.The roster, the equipment list and the local database file are excluded from version control by design, not by habit. The code is shareable; the data it reads is not.
  • Locked down on the database side too.On the hosted option, row-level security is enabled on every table with no policies attached, so the database's public API cannot read or write them at all. The application connects server-side instead. A reporting tool should not be the reason operator records become readable from the internet.
  • Kept the Excel export.The people who need to read the reports were spreadsheet users, and the fastest way to lose a system is to take away the format its readers trust. The export produces the same report from the database, which also makes it the migration bridge rather than a parallel process.
  • Replicated the workbook before improving it.The first version reproduced Kristofer Salcedo's formulas exactly, cell reference by cell reference, so that the output could be compared against the file people already believed. Improving the metric came after it was trusted, not before.

07 — Where it standsBuilt, running, and what comes next

  • Built.The form, the validation layer, the schema, the local and hosted storage paths, the Excel export and the shortcut the leaders use. Shift reports now accumulate as history rather than overwriting one file.
  • Feeding downstream.Stored shifts are what the productivity and equipment-availability dashboards read, which is what made comparing shifts, teams and operators possible in the first place.
  • Next.Authentication per leader so the report records who filed it rather than who it says filed it; a correction trail instead of a silent replace; and the data-quality checks that belong in the database rather than the form — operators appearing on shifts after they leave the roster, shifts filed for dates with no operation, equipment identifiers that stop matching the asset list.
